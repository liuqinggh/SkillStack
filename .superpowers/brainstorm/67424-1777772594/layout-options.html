方案 A：最大程度按截图复刻

左侧做完整工作台壳子，顶部品牌、搜索、模块分组、Agent 树、子会话列表全部做出来，中间区做文档式聊天。

优点

  • 视觉最像原图
  • 后续可平滑扩成真工作台

缺点

  • 组件拆分最多
  • 占位数据与状态管理更复杂

方案 B：推荐，先做真骨架

外观上高度接近截图，但只把 `Agents / 会话 / 附件 / 输入区 / SSE 聊天` 做成真功能，其它导航先做静态模块页。

优点

  • 投入产出比最好
  • 能直接复用现有 session / upload / runtime API
  • 后续扩展风险小

缺点

  • 不是 100% 逐像素复刻
  • 部分左栏目前仍是展示壳

方案 C：最快上线版

尽量不改数据结构，只给现有页面换皮，加一个较窄侧栏和更像文档的消息渲染区。

优点

  • 开发最快
  • 对现有代码入侵最小

缺点

  • 不像完整工作台
  • 后续再扩容时容易返工

我建议选 B

它像截图，但不会把项目带进“先修 UI 壳子，再补业务骨架”的经典前端泥潭。这个方案能直接映射你现有的 `sessions`、`uploads`、`runs` API，属于能跑、能演示、还能继续长的那种。
