第二部分：新版 API 设计与 SSE / WebSocket 分工

原则：先把“运行时协议”设计清楚，再决定具体实现细节。不要让前端直接和 DeepAgents / LangGraph 的内部事件打交道。

推荐的对外 API 面
POST /api/runtime/runs
发起一次 agent run，返回 run_id / session_id / status
GET /api/runtime/runs/{run_id}
查看一次 run 的状态、摘要、错误、最终输出
POST /api/runtime/runs/{run_id}/cancel
取消正在执行的 run
POST /api/runtime/sessions
创建会话，返回 session_id
GET /api/runtime/sessions/{session_id}
读取会话摘要、上下文、最近 run
POST /api/runtime/sessions/{session_id}/runs
在指定 session 内发起一次 run
建议的事件流协议
SSE
用于单次 run 的线性输出流：started, planning, delta, tool_call, tool_result, done, error
WebSocket
保留给未来的双向控制场景：中断、恢复、多人协同、前端实时控制台
当前阶段建议
最小闭环先上 SSE，不急着上 WebSocket。先把 run 事件模型定义稳，再考虑双向长连接。

请求模型建议

{
  "input": {
    "message": "帮我分析这段日志"
  },
  "agent": {
    "id": "general-assistant",
    "mode": "chat"
  },
  "model": {
    "provider": "litellm",
    "model": "claude-3-7-sonnet"
  },
  "session_id": "sess_xxx",
  "stream": true,
  "metadata": {
    "source": "web"
  }
}

为什么改成 run 语义

因为一次 agent 执行不只是“聊天回复”，还可能包含 planning、工具调用、技能命中、子代理结果。`run` 比 `chat` 更接近真实业务对象。

为什么 SSE 先行

SSE 更适合单向流式输出，和大模型 token / event 推送天然契合；前端实现简单，排障成本低。WebSocket 适合下一阶段，不适合最小闭环先上来就背。

为什么不保留旧 chat API

你已经明确允许重做接口，那就应该直接围绕 runtime object 设计，而不是把旧 `/chat` 勉强包装成一层新概念的壳。
