第一阶段最小闭环
必须做
runs API、sessions API、SSE 事件流、LiteLLM provider、DeepAgents runtime、session 映射、run 状态记录
先不做
WebSocket、复杂权限、后台管理台、技能市场 UI、多租户、分布式队列
保留演进位
tool trace、subagent execution trace、run resume、run cancel、agent registry

推荐迁移步骤

Step 1
引入 `providers` 与 `runtime` 基础层，不先拆全部旧代码。先让新版 `run_stream()` 可以通过 LiteLLM + DeepAgents 跑通。
Step 2
新增 `sessions` 与 `runs` 路由，正式引入 `session_id / run_id` 协议，同时保留旧代码仅供过渡测试。
Step 3
把现有 `deep_agent_adapter` 的能力分别下沉到 `providers + agents + runtime event normalization`。
Step 4
补 run 查询、错误封装、日志埋点、session repository；确认 SSE 事件模型稳定。
Step 5
删除旧 `/api/v1/chat` 体系和静态测试页，切换到新 runtime 协议。

为什么不是一次性重写

因为你当前项目已经能跑，只是结构还不够产品化。渐进式迁移可以让每一步都可验证，避免“重构完成时顺便把可用性也重构没了”。

为什么第一阶段刻意收缩

最小闭环的价值是把协议、运行时、状态模型先钉死，而不是抢先做一堆未来功能。先把骨架立住，再给它长肌肉。

为什么最终要删旧 chat 体系

你已经允许重做接口，那就不要长期双轨。双轨久了，代码会进入“新旧都支持，谁都不敢删”的技术债舒适区。
